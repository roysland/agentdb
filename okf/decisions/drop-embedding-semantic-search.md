## Context

agentdb originally shipped with optional embedding-based semantic search. Embeddings were generated by an HTTP provider (configurable: local llama.cpp, remote API, etc.) and stored in the `chunks` table alongside the chunk text. The system supported three search modes: lexical (FTS5/BM25), semantic (vector cosine), and hybrid.

In practice, the embedding pipeline triggered local firewall rules even when the provider endpoint was localhost. The infrastructure was substantial: a dedicated `internal/embed` package with provider abstraction and caching, `embedding_pipeline.go`, `semantic.go`, `--embed-*` CLI flags, `embedding_model` and `embedding` columns on the schema, and a `semantic_search` MCP tool. This complexity existed to serve a use case that was not core to agentdb's value proposition.

## Decision

Drop all embedding and semantic search support. Search is now lexical-only using FTS5 with BM25 ranking. The `EmbeddingModel` field remains on the `Chunk` struct and the schema retains `embedding_failures` as a dead column, but no code populates embeddings and no MCP tool exposes semantic search.

## Alternatives Considered

- **Keep embedding as opt-in behind a build tag** — would avoid the firewall issue for most users, but still carries the maintenance burden and code complexity for a rarely-used path.
- **Switch to a pure-Go embedding provider** — would eliminate the HTTP firewall issue, but embedding quality and model size make this impractical for a developer tool running locally.
- **Keep semantic search, make the HTTP provider optional** — the existing design already did this; it did not eliminate the firewall trigger.

## Consequences

- FTS5/BM25 search is the sole search mode. Keyword matches are fast and deterministic; relevance degrades for natural-language queries that don't share tokens with code.
- The `internal/embed` package, `internal/search/semantic.go`, `internal/search/embedding_pipeline.go`, and all related tests are deleted.
- The `EmbeddingModel` field on `Chunk` and `embedding_failures` in the schema are vestigial. They should be cleaned up if the schema is otherwise revised.
- If semantic search is ever needed again, it must be redesigned from scratch. The prior design should not be restored as-is.
